How I Built A Billing Pipeline That Can Prove Every Invoice Is Right, Down To The Cent

For engineers who handle money, or who let AI agents write their code: 1 million usage events, 2 replays with identical hashes, a live Salesforce org that matched the ledger to the cent, and the 2 bugs that taught me the most.

An invoice you can't recompute is an invoice you can't defend.

When a customer disputes a charge, pointing at a database row settles nothing. You need to show which events produced each line, how each one was priced, and that running the same math again gives the same number. I built a usage-metering pipeline around that single requirement, built it with the help of AI agents, then tried to break it with a million events and a real Salesforce org.

This post covers the four decisions that held up, the two bugs I learned the most from, and why this kind of proof matters even more when an agent writes the code.

01
Never edit raw events, so every invoice can be rebuilt from scratch.

Every usage event (an API call, a gigabyte stored) lands in an append-only table and stays there. Nothing updates it, and nothing deletes it.

Duplicates are the first problem. Producers retry, networks time out, and the same event shows up twice. Each event carries a client-supplied ID, and ingestion is a single INSERT ... ON CONFLICT DO NOTHING on that ID, so a producer can resend any batch without double billing. In the load test I sent 1,000,000 events with 10% duplicates from 8 concurrent clients. The pipeline ingested them at 38,568 events per second and stored exactly the 900,129 unique ones.

Because the raw log never changes, an invoice becomes a pure function of three inputs: the events, the cutoff time of each billing period, and the price plans. That makes the strongest test in the project possible. I replayed the full log of 999,589 events into an empty database, twice. Both replays rebuilt all 200 invoices, and every invoice's SHA-256 content hash matched the stored one and the other replay.

If your billing can't pass that test, you are trusting it rather than checking it.

02
Do money math in integer cents, and round exactly once per line.

In binary floating point, 0.1 + 0.2 does not equal 0.3. Worse, the error depends on the order of operations, so float money math can give different totals for the same inputs.

The pricing engine uses Python's Decimal for quantities and unit prices, and integer cents for every amount. Multiplication runs in a local decimal context with the Inexact trap turned on, so any precision loss raises an error instead of happening silently. A unit test fails if float appears anywhere in the rating code, and the constructors reject non-Decimal input.

Where you round matters as much as how. Rounding per event accumulates bias and makes totals depend on batch sizes. I round once per invoice line, half-up, and the invoice total is the sum of the rounded lines, so the lines always add up to what the customer sees. Hypothesis property tests pin the rules down: totals are never negative, never drop when usage grows, and are off by at most half a cent per line.

03
Book late usage on the next invoice instead of reopening the old one.

Usage keeps arriving after a month ends. A producer was offline, or a retry finally succeeded.

Reopening a sent invoice means versioning it in both the ledger and Salesforce, and customers see numbers change after the fact. Rejecting late events loses revenue and makes retries unsafe. So each month's close records a cutoff time, and an event for an earlier month that arrives after that cutoff becomes an adjustment line on the next invoice, labelled with the month it belongs to.

The adjustment is priced at the old month's marginal rate: the charge for (billed usage + late usage) minus the charge for billed usage alone, both under the old month's plan. Late usage that pushes a customer into a cheaper tier is priced in that tier. Late usage still under a minimum commit costs $0. Nothing is billed twice.

The cutoff is set 60 seconds in the past. An ingest transaction still in flight when the close starts has a timestamp before "now" but isn't visible yet, and a cutoff of exactly "now" would skip it forever. With the lag, it lands after the cutoff and gets billed as late usage next month.

Remember that 60-second lag. It shows up again in bug #2.

04
Treat Salesforce as a second ledger, and check it record by record.

Sales and finance teams live in the CRM, so invoices have to reach Salesforce. That makes Salesforce a second copy of the truth, and two copies drift apart unless something checks them.

Only aggregates go to Salesforce: accounts, one record per invoice, and usage summaries per customer and meter. Raw events stay in Postgres. Every write is an upsert keyed by an External ID, so a retried sync updates the same record and never creates a duplicate. Month-end close, sync and reconciliation run as jobs on jobq, the Redis and Postgres job queue I built in an earlier project. Failed jobs retry with backoff, and a job that keeps failing goes to a dead-letter queue (DLQ) instead of disappearing.

Reconciliation compares the ledger and Salesforce one record at a time, in integer cents.

I tested the unhappy paths on purpose. A forced Salesforce failure was retried by the queue and drift ended at zero. A longer outage sent the sync to the DLQ after 5 attempts, and replaying it from the DLQ brought drift back to zero. After 1 million events and two closed months, the ledger and Salesforce both totalled $29,403,835.60.

Those runs used an in-memory fake of Salesforce, which is what CI uses. So I ran it against a real Developer Edition org too: 20,000 events across two months, 100 accounts, 200 invoices and 400 usage summaries. I queried Salesforce directly, bypassing my own client, and it held $598,167.89, the same total as the ledger to the cent. The whole session used 110 of the org's 15,000 daily API requests.

05
The two bugs that taught me the most were in the plumbing.

The pricing math never produced a wrong number. Both real bugs came from the system around it.

Bug #1: a 205-second query fixed by one line.

An aggregator rolls raw events into hourly totals for the usage dashboard. To stay correct under retries and crashes, it recomputes every touched hour from all of that hour's raw events, using a temporary table of "dirty" hours.

At 900,000 events, one pass took 205 seconds.

The agent working on the load test ran EXPLAIN ANALYZE and found why. Postgres had no statistics for the freshly created temp table, so the planner guessed badly and joined each dirty hour against every event that customer had ever sent. Adding one ANALYZE on the temp table before the query brought the pass to 2.1 seconds. Autovacuum never analyzes temporary tables, so the planner knows nothing about one until you run ANALYZE yourself.

Bug #2: the first live run billed nobody.

The first time I pointed the full stack at the real Salesforce org, it ingested 20,000 events, closed the month, and produced zero invoices.

Nothing was wrong with the code. The demo script closes each month a few seconds after sending events, and it expects the stack to run with a 3-second cutoff lag, as CI does. The agent running the setup had started the stack with the default 60 seconds. Every event was still inside the safety window from section 3, so the close correctly treated all of them as too recent to bill.

Nothing reached Salesforce from that run. The agent spotted the cause, reset the stack with the 3-second lag, reran it, and got the zero-drift result above. Then we added a note to the setup guide, because the same guard that protects in-flight transactions will confuse the next person who runs a fast demo.

06
Proof matters more when an AI agent writes the code.

Using agents was the plan from the start. I scoped the project and did the research first: how billing systems handle late usage, how to round money, how Salesforce upserts and its Bulk API work. Then I built it with the help of AI agents. I gave them skills and rules they had to follow (free tools only, every number measured, nothing claimed that wasn't run), and I built a separate QA agent whose job was to test what the others wrote.

Agents write a lot of code quickly, and they can be wrong with total confidence. Both bugs above involved an agent: one caused the empty live run, and another found and fixed the 205-second query. Reading every line of a codebase this size doesn't scale, so the QA agent and I leaned on checks that don't care who wrote the code. Replaying the log has to reproduce every invoice hash. Property tests have to hold for any input Hypothesis generates. Reconciliation has to match Salesforce record by record. And the final total has to match when I query Salesforce directly instead of trusting the pipeline's own report.

Those checks turned "the agent says it works" into something I could verify in minutes.

The takeaway

Write the replay test before the invoice template.

If you build anything that charges money, make the replay test the first thing you write. Keep raw events immutable, make invoices a pure function of events, cutoffs and plans, and prove it by rebuilding everything from scratch and comparing hashes. Every other guarantee in this post depends on that one, whether a person or an agent writes the code.
