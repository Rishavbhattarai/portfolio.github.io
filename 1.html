What I built, in 30 seconds

A native Salesforce app for FundMate. A specialist creates a Funding Application from a business, and the app pulls in the owners and the last three bank statements. One button validates it and queues it. A batch job sends applications to the Underwriting API, 50 per callout, and writes the partner's status back on each record. The partner posts signed decisions to my REST endpoint, which creates Decision and Offer records, and a Flow routes the application to the right queue.

Underneath: no application is ever sent twice, even with two runs at once; retries follow Retry-After and reuse the same Idempotency-Key; every inbound request must pass OAuth, a custom permission and an HMAC signature; one bad record never fails the others; and logs survive rollbacks. Anything an admin might change, such as fields, thresholds and routing, is Custom Metadata or Flow, so it changes in Setup without a deployment.

3. The design in one minute1:30-2:30Data model, Custom Metadata
On screen: Chrome tab 3 (Payload Field Map, business.ein), then tab 4 (Routing Rules).

Account is the business and Contact is the owner, with SSN, EIN and date of birth encrypted. Bank statements belong to the business. When an application is created and again when it is sent, it snapshots the last three months, so underwriting always sees exactly what was sent.

Most of the behaviour lives in configuration.

Show: Setup → Custom Metadata Types → Payload Field Map → business.ein, then Routing Rule.

Each key in the API request is a metadata record: which object, which field, whether it's required, and the format. The validator and the payload builder both read it. Routing works the same way: status and amount range to a queue. Approvals over 250,000 go to Senior Funding, and partner rejections and send failures go to Integration Exceptions, as Deepak asked. Validation rules on the metadata stop an admin saving a broken setting.

So if FundMate raises the revenue minimum or adds a queue, an admin changes it in Setup and no code is deployed.

Under the hood: FundingApplicationSelector.fieldMaps() reads Payload_Field_Map__mdt and builds the SOQL. FundingApplicationValidator checks required + regex from the same records. UnderwritingPayloadBuilder groups by section. IntegrationConfig reads Integration_Setting__mdt.Default. Flow Route_Decided_Funding_Application reads Routing_Rule__mdt.

Why Custom Metadata, not Custom Settings or hardcoded values?

Custom Metadata deploys with the package, can be cached and queried without counting against SOQL limits, supports validation rules and is visible to Flow. Custom Settings are data, so they don't move between orgs with the code. The one exception is the signing secret, which is in a protected custom setting because secrets shouldn't be in deployable metadata.

Why are statements on the Account, not on the application?

Statements exist before any application and are reused across applications. I changed this after the questions email. The snapshot fields on the application freeze what was sent, so a later statement doesn't change history.

Why a separate Underwriting Decision object instead of fields on the application?

An application can get more than one decision (Needs More Info, then Approved). A separate record keeps the audit trail, and its unique Decision_Id__c is what makes duplicate detection a one-query check.

Why Classic Encryption, not Shield?

Shield is a paid add-on and not available in a Developer Edition. Classic Encryption masks on screen and only users with View Encrypted Data see the value. In production with Shield I'd use deterministic encryption so EIN can still be filtered.

Why is date of birth a text field?

Classic Encryption only works on text. A regex validation rule enforces YYYY-MM-DD and another enforces 18+.

Why Batch Apex, not chained Queueables or @future?

Batch gives every 50 records a fresh transaction with its own limits and one callout. One transaction gets only 120 s of total callout time and 100 callouts, Developer Edition caps Queueable chain depth, and @future can't be chained or monitored. Batch also shows up in Apex Jobs, which is my evidence.

Why a separate claim step before the batch?

Salesforce doesn't allow a callout after DML in the same transaction, and the lock must be committed before sending so a second run sees the rows as Queued. Claiming in its own transaction solves both.

Why FOR UPDATE and a re-read, not just checking Status?

Two runs can both read "Ready" before either writes. FOR UPDATE makes the second wait until the first commits; re-reading under the lock then finds them Queued and skips them. Checking status alone is a race.

Why send on a button and also every 15 minutes?

The button gives instant feedback for one application. The sweep catches everything else: bulk-loaded Ready records, retries longer than 10 minutes, and anything the button's job missed. Both go through the same claim, so they can't double-send.

Why does the partner's status go on the application?

The brief asks for Status and StatusReason upserted back. Keeping it on the record means a specialist sees it in list views and reports without reading logs.

6. Code walkthrough5:30-7:15About 20 seconds per file
On screen: VS Code, files under force-app/main/default/classes/.
UnderwritingClaimService.cls, the two FOR UPDATE queries.

The claim locks the rows, reads them again under the lock, and only moves the ones still Ready. In my org I started two send runs at the same moment: one batch ran, the other claimed nothing, and all 1,000 applications had a single batch key.

UnderwritingBatchSender.cls, sharedKey and retryBatch.

This sends one batch. The Idempotency-Key is created once per batch and stored on each application. On a 429, a 5xx or a timeout, the same batch is retried with the same key, which is what FundMate confirmed: the partner ignores a repeated key for 24 hours. When a user resends after fixing something, the key is cleared, so the partner never ignores a corrected application.

UnderwritingRetryJob.cls, execute.

The retry job resends exactly those applications after the wait: a delayed Queueable for up to 10 minutes, a one-off scheduled job for longer. Retry-After wins, otherwise exponential backoff with jitter. After five attempts the application is Send Failed and goes to Integration Exceptions with an alert.

UnderwritingDecisionResource.cls, the permission check, then SignatureVerifier.verify.

The inbound endpoint only accepts the integration user: the partner gets a token with OAuth client credentials, and any other token, even mine as admin, gets a 403. Then it checks an HMAC-SHA256 signature over the timestamp and the raw body before parsing anything. A missing, wrong or old signature gets a 401.

DecisionProcessor.cls, the process method.

Five steps, each one query or one DML for the whole request: shape check, duplicates, match the application and tracking id, check offer ids, then save with partial success. Every decision gets its own result, so one bad decision never blocks the others.

Why one Idempotency-Key per batch, not per application?

That's the partner's contract: the key goes on the request, and a request is a batch. Retries must resend the identical batch with the identical key, so the job stores the ids and key and resends exactly those.

When does an application get a new key?

A user resend (data may have changed, so it's a new request), and an application missing from a 2xx response (the partner may have stored the key without processing it, so the same key would be ignored).

Why full jitter?

If many batches fail at once, plain exponential backoff makes them all retry at the same second and hit the rate limit again. Random delay up to the cap spreads them out. Retry-After from the server always wins.

Why a Queueable delay plus a scheduled job for long waits?

Queueable delay maxes out at 10 minutes. Retry-After can be longer, so a one-off Schedulable starts the retry job at the right time. Schedulable can't call out itself, and a class can't be both, hence the small UnderwritingRetryScheduler wrapper.

Which errors are retried?

429, 5xx and timeouts are transient. 400, 401, 403 aren't: retrying won't fix them, so they go straight to Send Failed with the message and an alert. A missing Named Credential key also fails fast instead of looping.

Why OAuth and HMAC both?

OAuth proves who is calling. HMAC proves the body wasn't changed and, with the timestamp, isn't a replay. The custom permission makes sure only the integration user, not any logged-in admin, can post.

Why constant-time comparison?

A normal string compare stops at the first different character, so timing can leak how much of a guessed signature is right. Comparing every character removes that.

Why sign the raw body, not the parsed JSON?

Re-serialising changes whitespace and key order, so the signature would never match. And parsing before verifying means processing untrusted input.

Why a REST Apex endpoint, not the standard sObject API or Platform Events?

The partner shouldn't know Salesforce's schema, and the brief needs signature checks, per-decision validation and a result per decision. The standard API can't verify an HMAC or return "duplicate". Platform Events don't give the caller a synchronous answer.

How are duplicates handled?

One query for existing Decision_Id__c values plus a set for repeats inside the same request. A duplicate returns "duplicate" and writes nothing. The unique field is the backstop if two requests race.

Which applications can accept a decision?

Only Acknowledged and Needs More Info (a setting). The tracking id must match. Anything else is rejected with the current status in the reason.

Why partial success and also a savepoint?

Partial success (allOrNone false) is for expected bad records: each is rejected and the rest save. The savepoint is for an unexpected exception: roll everything back and return 500, so the partner can safely resend, and the request is never half-applied.

What if a decision saves but its offer fails?

That decision is deleted again and reported as rejected, so there's never a decision without its offers.

Why log through a platform event?

A normal insert rolls back with the transaction, so you'd lose the log of the error that caused the rollback. A Publish Immediately event is delivered anyway, and the handler upserts on the event UUID so redelivery doesn't duplicate.

Why route with a before-save Flow, not Assignment Rules or Apex?

The brief asks for Flow where admins should change behaviour, and routing is exactly that. Before-save sets OwnerId with no extra DML. Assignment Rules only work for Leads and Cases. The rules themselves are Custom Metadata, so an admin edits a row, not the Flow.

Why queues, not Omni-Channel?

Queues meet the brief and work in any org. Omni-Channel could sit on top of the same queues later to push work to available specialists.

Hard follow-up questions

What would you change for production?

(Suggested answer, make it yours.) Shield deterministic encryption, a real partner sandbox instead of the mock, Omni-Channel on top of the queues, a dashboard over Integration_Log__c, and rotating the signing secret with two active secrets during changeover.

What if 100,000 applications are Ready?

The claim takes up to 5,000 per run to stay inside the 10,000 DML row limit. The rest wait for the next run every 15 minutes. If that's too slow, run the claim more often or claim inside the batch start query.

What if the partner sends a decision before the Acknowledged response is saved?

The application is still Queued, which can't accept a decision, so it's rejected with the reason. The partner retries and it succeeds once the status is Acknowledged.

Likely interview questions

Why Batch Apex and not chained Queueables?

Each execute gets fresh limits and one callout per 50. Chained Queueables hit Developer Edition's chain depth, and one transaction allows only 120 s of callouts.

How do you stop two runs sending the same application?

FOR UPDATE locks the Ready rows, the claim re-reads them under the lock and only moves the ones still Ready to Queued with its batch key, before any callout. The second run finds nothing Ready.

What if the callout times out but the partner got it?

The retry sends the same applications with the same Idempotency-Key, so the partner ignores the repeat for 24 hours.

Why does the log survive a rollback?

Logs are published as a platform event set to Publish Immediately; a subscriber writes Integration_Log__c in its own transaction.

Why verify the signature before parsing?

The HMAC is over the raw bytes. Parsing first wastes work on forged requests and re-serialising could change the bytes.

The algorithm, end to end

A. CREATE
 1. Business (Account) with owners (Contact) and monthly Bank_Statement__c.
 2. "New Funding Application" flow inserts the application.
 3. Before insert: Status = Draft; copy the latest 3 statements into the
    snapshot fields. Formulas give average deposits and the revenue flag.

B. SUBMIT AND VALIDATE
 4. "Send to Underwriting" → SendToUnderwritingAction (reads in user mode)
    sets Status = Ready.
 5. Before update (to Ready): snapshot again, then
      errors = FundingApplicationValidator.validate(app)
      errors?  Status = Validation Failed, reasons in Status Reason. Stop.
      none?    reset Retry Count, Next Retry At, Idempotency Key.
 6. Enqueue UnderwritingDispatcher (the schedule also does this every 15 min).

C. CLAIM (never send twice)
 7. Send Enabled off → log and stop.
 8. batchKey = new UUID
    SELECT Ready (retry time passed) FOR UPDATE
    SELECT the same rows again FOR UPDATE; keep those still Ready
    UPDATE → Queued, Batch Key = batchKey        (before any callout)
    A second run waits on the lock, then finds nothing Ready.
 9. executeBatch(UnderwritingSendBatch(batchKey), 50)
    1,000 applications = 20 executes, each with its own limits, 1 callout.

D. SEND ONE BATCH
10. Load application, business, owners at 20%+, statements.
    key = the batch's shared Idempotency Key, or a new UUID.
11. Body from Payload_Field_Map__mdt.
    POST callout:Underwriting_API/v1/applications/batch
    Headers: X-Api-Key (Named Credential), Idempotency-Key; timeout 20 s.
12. 2xx: match each result by applicationReference
          Acknowledged → Status, Tracking Id, Sent At
          Rejected     → Rejected (routed to Integration Exceptions)
          missing      → back to Ready with a new key
    429 / 5xx / 408 / timeout:
          attempt = highest Retry Count + 1
          attempt ≥ Max Attempts → Send Failed, alert
          else delay = Retry-After (capped)
                       or random(0, min(base × 2^(attempt-1), cap))
               stay Queued, store Retry Count and Next Retry At
               delay ≤ 10 min → enqueueJob(RetryJob, minutes)
               delay  > 10 min → one-off scheduled job → RetryJob
               RetryJob resends the SAME applications with the SAME key
    other 4xx or bad config → Send Failed, no retry, alert
13. Database.update(..., false): one bad row doesn't block the rest.
    Log with a limits snapshot.
14. finish(): run summary; alert the owner or queue members and
    Integration Admins (bell notification and email).

E. RECEIVE  POST /services/apexrest/underwriting/decisions
15. OAuth client credentials as the integration user.
    No FundMate_Post_Underwriting_Decisions → 403.
16. Secret from the protected setting. Missing headers, timestamp off by
    more than 300 s, or HMAC-SHA256(secret, ts + "." + rawBody) not equal
    to X-Signature (constant-time) → 401.
17. Not JSON or no "decisions" array → 400. More than 500 → 413.
18. Savepoint, then DecisionProcessor:
      a. check shape and offers               → rejected with a reason
      b. decisionId seen before or repeated   → duplicate, nothing written
      c. unknown reference, wrong status, trackingId mismatch,
         second decision for one application  → rejected
      d. offerId already used                 → rejected
      e. insert decisions, then offers (allOrNone false);
         an offer fails → delete that decision and its offers
      f. mark the application's older offers Superseded
      g. application Status = decision, Decided At, Status Reason
    200 {received, created, duplicate, rejected, results[]}
    Unexpected error → rollback, log (survives), 500 "safe to retry".

F. ROUTE
19. Before-save flow: rules for this status, active, by priority;
    first where Min ≤ Requested Amount ≤ Max → OwnerId = queue.
    No match → note it in Status Reason.

G. OFFERS
20. Offer trigger sets Estimated APR. offerComparison LWC shows offers
    side by side, best value per row, superseded on request.

H. OPERATIONS
21. Errors and limits → Integration_Log_Event__e (Publish Immediately)
    → upsert Integration_Log__c on the event UUID. Text goes through
    redact(): SSN, EIN, DOB, deposits, keys.
22. 2 AM purge deletes logs older than 90 days, 9,000 per run.

Likely questions

Why Batch Apex, not chained Queueables?

Developer Edition caps the chain depth, and one transaction gets only 120 s of callout time in total. A batch gives each 50 their own limits.

How do you stop a double send?

The claim locks with FOR UPDATE, re-reads under the lock, and moves Ready to Queued with a batch key before any callout. After a timeout the retry sends the same Idempotency-Key, and the partner ignores a repeat for 24 hours.

Why clear the key on a user resend but keep it on a retry?

A resend may carry corrected data, so it's a new request. A retry is the same request.

Why log through a platform event?

A normal insert rolls back with the transaction. A Publish Immediately event is delivered anyway.

Why OAuth and HMAC both?

OAuth proves who is calling. HMAC proves the body wasn't changed and isn't a replay.

Why 11 classes without sharing?

System processes must see private, queue-owned records. Each one has a reason in the README. The user entry points, the Send action and the offer controller, run in user mode.

Why is date of birth a text field?

Classic Encryption only works on text. A regex validation rule enforces the format.

What changed after your questions email?

Statements moved from the application to the Account, with a snapshot on the application, because they exist before any application. Needs More Info can take a second decision that supersedes older offers. Rejections and send failures got their own Integration Exceptions queue, from the product owner's answer.

The one-paragraph answer

Apex does the work that needs code: the integration, scale, security and logging. A send run claims Ready applications under a lock, then a batch sends them 50 per callout through a Named Credential and writes the result back on each record. Retries follow Retry-After and reuse the same Idempotency-Key. Decisions arrive at a REST endpoint that checks OAuth, a custom permission and an HMAC signature, then a processor saves each decision on its own so one bad decision never blocks the rest. Logs go out as a Publish Immediately platform event, so they survive a rollback. Routing and screens are in Flow.

Likely questions

Why is routing not in Apex?

The brief says admin-changeable logic belongs in Flow. Route_Decided_Funding_Application reads Routing_Rule__mdt, so queues and thresholds change in Setup.

Why split UnderwritingSendBatch and UnderwritingBatchSender?

The batch handles scope and run totals; the sender handles one batch. The retry job reuses the sender, so first sends and retries follow the same rules.

Why a separate claim transaction?

You can't make a callout after DML in the same transaction, and the lock has to be released before the send so the second run can see the rows are Queued.
